# 対応の優先順位

実装はまだ行っていない。着手順の提案。

## 1. 配信の手前では止められない

2026-10-26 の確認で、独自ドメインは Cloudflare に載せておらず、WAF は入っていない。本番 URL は `https://depositmanagement.pages.dev` で、`pages.dev` 側に利用者が WAF ルールを追加する余地はない。

同じ日、未ログインで `/api/facilities` を叩くと 401 が返った。入り口のログイン判定は本番で動いている。WAF が無いので、その判定を飛ばすリクエストはアプリまで届く。

## 2. ログイン確認を API ハンドラにも置く

版を上げても、認可が middleware だけだと、次のミドルウェア回避で同じ構造が再発する。入出金の作成・更新、利用者、インポート、印刷のように預り金データへ触るルートは、ハンドラ側でもセッションを要求する。

空床の公開 API は API キー検証が既にある。そこはミドルウェア迂回の影響を受けない。

## 3. 14.2.35 は途中の版として扱う

14.2.16 から 14.2.35 へ上げると、CVE-2025-29927 と 2025年12月のサービス停止（CVE-2025-55184）は 14 系の修正範囲に入る。

14.2.35 は 14 系の最終版で、サポートは終了している。2026年5月の CVE-2026-23870 など、14 系に修正がない項目は残る。

## 4. サポートされている版への移行は別作業

2026年5月以降の修正を取り込むには Next.js 15 または 16 へ移る。2026-10-26 時点で案内されている修正済みの線は、15 系が 15.5.28、16 系が 16.4.1。

このリポジトリは `@cloudflare/next-on-pages` 1.13.16 でビルドする想定になっている。Next.js 15 以降は、このアダプタが追従しているかを別に確認する。追従していない場合は、Cloudflare 向けの後継アダプタ（OpenNext）への載せ替えが先になる。`next-auth` 5.0.0-beta.30 の peer は Next.js 14 / 15 / 16 を宣言している。

移行の前に、API の認可をハンドラへ移す作業は 14 系のままでできる。
